The model proposes, the runtime decides

The prompt-injection defense follows the CaMeL pattern (Debenedetti et al., 2025). The language model never executes anything. It writes an intent, such as [LER_ARQUIVO]: nota.txt. A deterministic core turns the intent into a typed plan, checks where each argument came from, scores the risk of the concrete action and then runs it, asks, or refuses.

Each value's trust comes from its origin, defined in a single table in the code. Combining values keeps the lowest trust, and reloading a record from disk recomputes trust from the stored origin. A property test over 500 random programs checks that no transformation raises it.

  • Risk is scored on the concrete action: reading a file is LOW, git status is HIGH (every shell command asks for confirmation), git reset --hard is CRITICAL. A tool with no declared risk is forbidden, and no confirmation unlocks PROHIBITED.
  • A confirmation creates a record bound to the SHA-256 hash of the tool plus its sorted arguments, valid for 120 s and usable once. Approving git status does not approve git commit.
  • A second axis tracks secrecy (PUBLICO, PESSOAL, SECRETO: public, personal, secret). Detectors for Brazilian CPF numbers, cards, private keys and tokens tag the value, and a SECRETO value never reaches the network, the voice, the terminal or an external provider.
  • Fail closed: an exception during authorization turns on Safe Mode and denies. PowerShell commands go through a parser and an allowlist, and run inside a Windows Job Object with memory and process limits.

For the adversarial evaluation I crossed the 16 attack families from the AgentDojo corpus with 4 hostile origins and 7 privileged sinks, and no combination got through. I added 38 vectors of my own in 7 categories: tag injection, PowerShell, paths, memory, screen, MCP and exfiltration. This shows the barriers hold against published injection families; I have not run the official AgentDojo benchmark.

One turn, from voice to answer

Ollama's cache only reuses the identical leading part of two requests. I moved the clock and per-turn context out of the system prompt so the prefix stays stable. Time to first token dropped from 12.6 s to 3.0 s on qwen3.8:27b (−76%) and from 336 ms to 131 ms on gemma4:e2b, and it no longer grows with the conversation.

Architecture and method

I run OBEY as tech lead, with AI agents writing parts of the code. That is why every fix follows the same routine: reproduce the defect in a throwaway temp directory, write the failing test, fix it, remove the fix to watch the test fail again (manual mutation) and run the full suite. The technical guide has 134 claims tied to executable checks, and all 134 pass.

What is not guaranteed yet

  • The Job Object limits memory and processes but does not isolate files, network or privileges. That is why CRITICAL actions are refused instead of running with weaker protection.
  • The audit trail has no hash chaining, so anyone with disk access can edit it.
  • On the tag path the plan only receives literals written by the model, which start as MEDIUM even when copied from a hostile page. Against web injection, protection comes from the quarantine, the tainted-conversation flag, the command allowlist and human confirmation.

Next step: a Windows process container for the cloud models (Claude, Gemini) and for commands.

METEO-SOL

Rebuilding 366 days of sunshine duration in Porto Alegre with a Random Forest, shipped as a desktop app.

Role

Data

Stack

Technical dossierPDF, 14 pages, in Portuguese (PDF, opens in a new tab)

INMET's automatic station A801, at the Porto Alegre Botanical Garden, measures global solar radiation every hour but has no sunshine recorder. Conventional station 83967 sits at the same spot (−30.0536°, −51.1747°, 41.18 m) and records daily sunshine duration. Between 2022 and 2025 it missed 394 days, 363 of them in 2025.

Because both stations share the site, terrain, local clouds and microclimate are the same for the predictor sensor and the target sensor. I used the 1,061 days when both worked to teach a model to estimate sunshine hours from A801's sensors. The WMO counts sunshine duration as the time direct irradiance stays above 120 W/m²; the model maps the day's integrated energy and the air's temperature and humidity state onto that duration.

Four scripts, each one auditable

  1. 01_exploracao.py

    Reads INMET's CSVs, drops the 10-line header and finds 14,904 negative pyranometer readings at night, caused by radiative cooling.

  2. 02_preprocessamento.py

    Applies max(0, R) before summing, aggregates 35,064 hours into 1,461 days and builds 3- and 7-day rolling means of temperature and humidity.

  3. 03_modelo_treinamento.py

    Joins the stations (1,061 complete days), splits 80/20 with seed 42 and trains a 100-tree RandomForestRegressor on 10 predictors.

  4. 04_predicao_final.py

    Loads the serialized model without retraining, handles the rolling-window edges and writes the final 1,433-day table in INMET's format.

Why a Random Forest: radiation alone already correlates at r = 0.917 with sunshine duration, but on broken-cloud or foggy days the link between accumulated energy and hours above 120 W/m² stops being linear. The trees capture the interaction with humidity and temperature range without normalizing quantities in different units (kJ/m², °C, %, m/s, mm).

The model (Joblib, 6.19 MB) ships inside a Windows executable built with Eel, Plotly and PyInstaller. Bioscience researchers open the 1,433-day series, zoom into periods on the chart, export the CSVs and read the source of all four scripts inside the app, with no Python install. In the final file the estimated column is named Insolacao_Prevista_h, kept apart from the measurements, so anyone citing the data knows what came from a sensor.

Limitations I have already mapped

  • The 80/20 split is random. Neighboring days are autocorrelated and the rolling means share days, so the test score may be optimistic. The next version should use temporal block validation (leave-one-year-out).
  • Wind accounts for 1.26% of importance and still cost 28 days. A secondary model without wind would recover those dates.
  • The model is calibrated to Porto Alegre's latitude and cloud regime. Another city needs recalibration on a co-located pair of stations.

Predicting antifungal resistance

ML models linking a yeast's sampling environment and genome to its antifungal resistance profile, for One Health genomic surveillance.

Fellowship
BIT/CNPq, September 2026 to August 2027
Advisor
Prof. Lívia Kmetzsch Rosa e Silva
Where
ResGen Initiative, UFRGS Biotechnology Center (CBiot)
Stack
Python, pandas, scikit-learn, SHAP, PCA, VCF, Django, Joblib

The project starts from 119 yeast isolates of the genus Candida sampled in the Arroio Dilúvio stream in Porto Alegre between 2023 and 2026, all with whole genomes sequenced. For each isolate I join sampling date and coordinates, phenotypic susceptibility profile, INMET weather data, water physicochemical parameters, antimicrobial quantification and landscape ecology such as land use and urban density.

The question is whether the sampling environment predicts each isolate's category (susceptible, intermediate or resistant), and which genomic mechanisms show up alongside each environmental pressure.

  1. Sep to Nov 2026in progress Python pipeline to extract, clean and normalize environmental, phenotypic and genomic data from ResGen DB, a relational database.
  2. Dec 2026 to Feb 2027 Imputation and normalization, Pearson or Spearman correlation, PCA. Supervised classifiers in scikit-learn with hyperparameter tuning and k-fold cross-validation.
  3. Mar to May 2027 SNPs, copy-number variants and ploidy changes, read from VCF files and encoded as feature matrices. SHAP and feature importance to link environmental variables to resistance mechanisms.
  4. Jun to Aug 2027 The best model, serialized with joblib or pickle, wired into ResGen's Django back end as a proof of concept for an analytics module.

Today the project sits at level 2 of the Technology Readiness Level scale: the concept is formulated and there is no analytical proof of concept on this data yet. By the end of the fellowship the goal is TRL 3, with a validated and documented pipeline that a future API in the ResGen DB dashboard can build on.
